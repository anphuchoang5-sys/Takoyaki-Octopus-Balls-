## 自验证结果

已完成37个串行隔离浏览器实验，174次阶段采样；全部原始报告保留。沙箱首次Chrome启动`spawn EPERM`，同一已审查命令经沙箱外自动审批后运行；这是基础设施失败，不是产品故障。一次PowerShell汇总命令空管道语法错误已修正，没有改写测试数据。

原脚本短回路实际结果：12栋clear-initial 1593.95、clear-steady 1417.72 MiB，exit1/MEMORY_HIGH；三栋1039/981 MiB、exit0。没有雪Worker，实际PAGE_CRASH为0。短晴天回路可捕获高占用，尚不具备复现用户实际OOM的反馈；本轮只对高占用/卡顿继续归因，不宣称已最小化OOM。

### 排序假设与可证伪预测（实验前说明）

1. 固定浏览器/渲染资源底座大：空浏览器→空编辑器出现阶跃；隔离去除后处理/阴影/缩略图可定位部分来源，不能用实验关闭作为正式修复。
2. 独立建筑资源重复、合批后原几何仍被所有权集合持有：单类1/6/12阶梯和资源字节随实例增加；仅移除合批后不再被场景使用的几何强引用，应降低GC后的主线程后备字节而保持实际显示几何计数。
3. 动态峰值来自准备/工作区/传输/显示同时存活及回收延迟：Worker生命周期字节与主线程显示/传输应有明确重叠；清雪资源归零不等于进程提交立即归还。
4. 生成提速增加交付后的查询/上传/阴影工作：计时边界和交付计数同时增加；仅隔离去掉阴影后对应渲染成本应明显下降。仍需区分总回归与局部因果。

基础阶梯已完成14项，全部无雪。空浏览器约213–221 MiB；空编辑器783.89；12格草地869.10。单类1/6/12：樱家842/1175/1468，みつや922/1376/未到稳态（首次2104触发1900保护停止），便利店795/834/819。混合2/6/12：823/1211/1428。单次值不拟合精确每栋斜率，尤其回收时机有差异；已证明类型不能互换。保护停止是采样后执行，可能越过1900，仍不是实际OOM。

资源与隔离实验结果：12栋可达场景数值缓冲73.55 MiB，按内容指纹统计重复53.86 MiB；材质1392、几何1869，纹理图像按RGBA估算65.35 MiB（逻辑尺寸，非实际显存）。合批所有权集合中不在场景树上的几何分别计数约39.93 MiB；仅移除这些引用的两次GC对照，后备缓冲132.5546→111.0956 MiB，差21.459 MiB，JS对象堆约64→48–50 MiB；可达显示几何字节/数量不变。39.93不能直接作为可释放量，因为存在其他引用或缓冲交叠，尚未逐条区分。进程总量首组反升22 MiB、复测降69 MiB，不能声称稳定省40/70 MiB。

空场景首次缩略图隔离：基准/跳过缩略图约758/441 MiB；延长15秒另一组约594/436，差值缩小，证实部分是热身/延迟回收。正式代码已调用renderer.dispose与forceContextLoss，不能把该实验解释为已证明漏dispose或驱动泄漏。混合12栋跳过缩略图两次约1331/1340，基准两次约1428/1429，改善约90–97 MiB但仍高于1200；不能用空图差值外推全部地图。

新脚本新增可选资源计数/GC/延时/操作系统进程核对；与无包装基准分开。雪面诊断生成本轮独立source目录，使用原脚本的source-dir机制，测量Worker生成/打包/缓冲、主线程接收/复制/索引、天气/阴影扫描/提交与GPU计时；不是正式性能结果。汇总脚本只读原始输入，输出新文件，旧结果不覆盖。

## 测量工具审计与环境

- Chrome 155.0.8059.85，V8 15.5.35.25；NVIDIA RTX4060 Laptop、驱动32.0.15.9159、ANGLE D3D11；1280×800、DPR1。临时profile，页面`http://127.0.0.1:4173/?review=snow`。所有新浏览器仅访问已有本地服务，测试地图为合成数据。没有检查个人浏览器、用户实际地图、其他窗口页面或更改机器/GPU设置。
- 进程指标是`SystemInfo.getProcessInfo`所列PID的`PrivateMemorySize64/1048576`之和。174次采样未见重复PID、已报告PID未读到数据或正式键非空。**不能严格称完整Chrome进程树**：OS父子关系实测8个chrome.exe，而CDP列7个，漏掉`crashpad-handler`约2.48 MiB。保持历史口径不补写旧数据，差额不足以解释高占用。
- 两个额外renderer对应隔离Chrome自己的`chrome://omnibox-popup...`浏览器UI，about:blank也存在，属于固定底座；没有混入用户其他Chrome窗口。OS核对只读本轮浏览器后代PID/类型/字节，未输出完整命令行。证据`process-audit.json`及`empty-base-late.json`。
- 私有提交不是物理内存/显存。WorkingSet包含可共享页，不将其总和当作独占物理内存。主线程与Worker的`usedSize/backingStorageSize`是另一个口径，不能再加到进程PrivateMemory上。主线程`backingStorageSize`也不只包含可见几何；未把它全称为雪缓存。
- 原脚本每阶段结束才采样，并非固定周期连续监控。PowerShell取进程、JS读取场景、CDP读取堆依次发生，时间点非原子；动态期间可能继续计算。1900保护在采样后判断，允许出现2104才停止的观测，不能称硬内存限制。最新三轮约124.6秒，也不是长时稳定性检查。
- 基础阶梯的`clear-steady`只是ready后约4秒采样；延时实验说明15秒后还能下降。不能把这个标签当作已达严格热稳态。原压力脚本额外测至少180个RAF间隔/指定时长，同名阶段与阶梯协议不混算收益。
- RAF指标是回调间隔，非GPU完成/实际呈现率。新增GPU timer包围composer渲染，异步读已就绪查询、最多8个未完成查询、检查disjoint；本轮成功采集且disjoint为0。它也不是屏幕呈现率。`renderSubmit`墙钟耗时包含驱动/背压等待，不能全部称纯JS计算时间。
- 计时实验的阶段差分包含阶段间等待及取样间隔（积雪约6.6–6.7秒），表中RAF仍取原约6秒窗口；分母不同，不能把计时累计直接除以RAF帧数。`queryIndex`嵌在天气查询内、GL调用嵌在renderSubmit内，不能重复求和。
- 旧`getSnowRevision`每个实例安装都会递增，不等于Worker消息数。六栋一份生成结果通常安装两次；12栋通常四次。新报告单独记录实际接收数。`requestedMaps`是阴影刷新请求，关闭阴影实验中因从未完成而反复请求，不能当实际画图次数。
- 原GL包装采用弱引用、不在报告中保留WebGL对象；本轮普通基准不启用GL包装/Profiler/GC，资源清单只返回计数/字节/摘要。计时报告有界保存数字日志，可能扰动JIT/调度；因此不取代正式前后性能表。新12栋GL计时也单独标记。

口径依据：[Microsoft PrivateMemorySize64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.privatememorysize64)、[CDP Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/)、[SystemInfo](https://chromedevtools.github.io/devtools-protocol/tot/SystemInfo/)、[Chrome Headless](https://developer.chrome.com/docs/automation-and-testing/headless)。官方资料说明当前headless与headful共享Chrome实现，但本轮仍未验证前台DPR/合成调度和真实地图差异。只查询公开技术口径，没有外发源码。

## 雪面生命周期、动态内存与耗时

| 阶段 | 创建/持有者、同时存活与释放 |
| --- | --- |
| 原建筑→承雪源 | 正式实例持有原几何；非零雪首次`collectSnowSource`临时采集局部Float32位置/Int16部位，init传输后主线程缓冲脱离；无雪不创建雪Worker |
| Worker准备 | 单Worker的models持有三类准备数据；解压文件的四个TypedArray是同一底层buffer的视图，不能逐buffer重复相加；本轮有效准备字段约26.69 MiB |
| 生成/打包 | workspace、hash/remap和返回缓冲在生成期间同时存在；六栋最大观测工作区76.80 MiB、hash/remap12.24 MiB、回收池32.05 MiB、单份返回数据最多32.05 MiB。各自最大值不同事件，禁止相加冒充同时峰值；传输的视图长度也不必等于整个后备容量 |
| 主线程接收 | 收到的新传输数据与当前显示几何同时存活；容量/全引用条件满足时复用显示属性，再复制数据、计算包围球、安装到实例；未替换完的旧雪量帧仍须保留，最后引用消失才dispose/recycle |
| 上传与查询 | 原传输属性返回Worker；显示属性保持主线程数组并更新GPU缓冲。当前顶面索引引用显示位置，查询分箱首次使用时重建；换帧清旧lookup。不能把每个实例的同源memory字节累加 |
| 阴影与绘制 | 新几何attribute/version进入全局caster快照，会让所有跟踪阴影图失效；下一render更新真实阴影及场景。不是闲置阴影未释放的旧问题 |
| 清雪/销毁 | 最后client释放source/frames；sources清空时终止Worker。应用逻辑资源归零后，JS垃圾回收和原生分配器归还可以滞后 |

### 上一轮内存下降但FPS下降：因果边界

六栋旧版带相同计时的复测：77.75 FPS、GPU6.02 ms/帧、35实例更新、75阴影请求；新版72.17/72.67、GPU6.47/6.52、46/49实例更新、100/105请求。查询索引旧16次211 ms，新21/22次262/290 ms，确实形成额外工作。

但旧版第一次同协议仅47.84 FPS、GPU10.67 ms，连不更新雪面的稳定满雪也显著变慢；这是不支持简单单因素归因的结果，完整保留，不能剔除后只引用漂亮配对。机器其他负载/频率可能影响，但本轮未控制或测得，原因仍未知。

新版单变量关闭阴影的实验80.58 FPS、GPU5.56 ms（当前两次约72、6.5），实际平均绘制调用约1890→1721；天气/查询工作仍在。它支持阴影对动态绘制有成本，但仅一次剥离实验、画面已不同，**不是生产修复，也不足以解释历史所有FPS差异**。下一步需相同交付序列回放或对各阶段进一步隔离，不能靠降频/延迟显示达标。

## 研究结论

有 WebGL/Three.js 内存上涨最终崩溃的相似报告，也有实时积雪算法。但本轮没有找到已复现、可直接对应本项目厚雪生成器的公开同一 bug；历史案例只能帮助选择调查方向。没有证据表明网页雪景天然只能支持六栋建筑，也没有依据承诺换一个算法就绝不崩溃。

### 2. 当前代码已经做了什么

- [snowfall.js](../../dist/town/editor/snowfall.js) 使用一份六角雪花几何和 InstancedMesh；每个有效格 96 片。雪花首次接触当前表面后隐藏并在下个周期复用，不会把每片落雪永久堆成新模型。每帧仍更新矩阵和查询实际落点；查询用的表面索引属于加速数据，不是无限保存每片历史落点。
- [snow.js](../../dist/town/assets/shared/snow.js) 已按素材版本共享承雪来源和引用计数雪面，有界任务队列只保留最新请求；一个共享 Worker，不是每栋一个 Worker。雪量按 0.005 档请求更新，并非每帧都重建几何，也不缓存全部 200 档雪面。
- [snow-worker.js](../../dist/town/assets/shared/snow-worker.js) 已有离线承雪数据、复用工作区、顶点精确去重、输出缓冲回收与可转移 ArrayBuffer。转移的资源所有权会移动，不再复制一份，这是 [MDN Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects) 描述的机制；再次建议“加 Worker/零拷贝”不足以解释剩余收益。
- [rain-surfaces.js](../../dist/town/editor/rain-surfaces.js) 和 [snow-surfaces.js](../../dist/town/assets/shared/snow-surfaces.js) 已按建筑局部表面和空间网格查找候选三角形，再做实际高度插值；旋转、搬动通过变换处理。同版本建筑共享基础落点索引。
- [snow-geometry.js](../../dist/town/assets/shared/snow-geometry.js) 的 `setAmount()` 仍遍历承雪面、裁切覆盖边缘、计算厚度、封闭边界和法线，再打包整套结果。主线程接收结果后仍创建新的 BufferGeometry/BufferAttribute；旧显示结果、生成工作区、新结果在更新过程可能同时存在。此为生命周期事实，不等于已证明剩余进程内存全由这里造成。
- `takeFrame()` 额外导出每个顶面三角形的 9 个 Float32 坐标供查询；显示几何同时保存对应顶点及索引。这里有继续消除重复数据的明确入口。

已有[上轮实测记录](2026-10-22-C-resident-memory-optimization.md)显示：12 栋稳定厚雪夜晚约 1529 MiB，持续积雪约 1795 MiB，雨中融雪约 1842 MiB。它们是隔离 Chrome 全部进程私有提交量的阶段采样，包含 GPU 进程；不是雪独占、物理 RAM 或瞬时连续最高值。由此推断动态更新值得优先研究，但还需分配采样确认各部分贡献。当前完整原始证据在 [comparison.json](../../artifacts/editor/resident-memory/comparison.json)。

### 3. 推荐的具体技术路线

以下为基于外部资料与本地源码的工程判断，未实现、未测得新收益。按能否保留现有输出与改动风险排序。

| 优先级与方法 | 具体措施 | 保真条件／风险 |
| --- | --- | --- |
| 第一：索引化查询，显示与落点共用坐标 | 保留现有精确表面与网格索引，让查询引用打包后的 positions，并用顶面索引识别三角形；不再独立复制 top 的全部坐标 | 保留三角形顺序、容差、最高命中选择、部位遮罩和实例变换。若有 T 个顶面，坐标副本当前约 36T 字节；3 个 Uint32 顶点索引约 12T，理论少 24T 字节，非整页可节约量承诺 |
| 第二：稳定 GPU 缓冲与有界复用 | 生成端保留原裁切/厚度算法；显示端按素材与必要帧所有权复用固定容量几何/属性，更新内容、drawRange 和 material groups，减少新建/删除 GPU 缓冲 | 缓冲容量需覆盖薄雪裁切时的峰值，不能只按满雪估计；不为每栋永久预留最大两份大缓冲。多实例旧帧仍被引用时不可提前覆写或转移其 ArrayBuffer；只回收无使用者的数据。复用会保留容量，是否净省内存必须实测 |
| 第三：固定拓扑区间内增量更新 | 从实际 score 阈值判断覆盖连接关系何时改变；关系不变时复用拓扑及映射，只重算改变的高度、法线和颜色；跨阈值才回退原裁切路径 | 不能把尚有孔洞的薄雪强行用整块壳代替。三角形退化、精确去重映射、法线焊接变化也属于失效条件，不能仅看雪量高低。全局雪量改变可能需要更新全部顶点，“增量”不保证只动少数点 |
| 第四：分部位参数化／高度场＋GPU 位移小样 | 道路和大屋面保留固定承雪网格，以表面字段与统一雪量驱动真实位移；檐口、洞口、灌木层次保留适合自身的封闭几何 | 单张全镇最高高度图不能表示多层屋檐、叶间空隙和复杂侧面；GPU 改高度也要同步法线、阴影、落点查询。若 GPU 画面与 CPU 查询各一套公式，精度差和读回成本可能抵消收益，须先独立小样 |

前两项主要改变表示与资源生命周期，可用现有几何逐项等值比较。第三项减少生成运算，但实现复杂度更高。第四项可能更大幅改变更新方式，不能提前称为无损。依据来自 [r180 索引几何说明](https://raw.githubusercontent.com/mrdoob/three.js/r180/docs/api/en/core/BufferGeometry.html)、前述更新源码与 NVIDIA/UEA 研究；具体排序和表中方案是本项目推断。

另外，同种建筑静态几何/纹理的安全共享、释放合批后不再需要的构造几何，仍值得检查，但不会自动解决不同建筑种类增多后的成本。已有雪面共享无需重复实现；多栋使用同一几何也不代表绘制提交自动合并。Three.js 的 [InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html) 要求相同几何与材质组合，正式整栋合批需兼顾独立材质、灯光、门与选中效果，不宜直接全场景替换。

### 4. 暂不推荐作为主解法

- **直接换 BVH。** [three-mesh-bvh 作者文档](https://github.com/gkjohnson/three-mesh-bvh)说明它加速空间查询，但动态几何需重建或 refit，且自身占用索引空间。当前已有适合竖直落点的空间网格，是否更快要测，不能把它称为内存问题的万能修复。
- **增加 Worker 数量。** 当前串行共享已控制峰值，增加并行生成会增加同时存活的工作区；主线程更顺畅不等于总内存更小。
- **直接迁移 WebGPU。** 官方粒子示例可参考，但引擎迁移不自动消除重复资源、积雪几何和渲染目标；兼容现有材质、灯光和编辑器的工作量不能隐藏。
- **缓存所有雪量档位。** 快速切换会换来大量常驻几何，违背本次内存目标；离线只保存静态承雪信息和必要容量/阈值元数据，不保存 200 套完整雪面。
- **把雪改成白色材质、减少建筑/雪花细节、直接降低坐标精度或分辨率。** 不符合当前保真要求；不能将这些收益写成无损。
- **把雪逐粒做完整物理模拟或全镇体素化。** 当前规则是统一雪量驱动外观，并不需要逐片雪决定堆积；引入更重的模拟没有本轮需求依据。

### 5. 下一轮最小验证

先试“共用查询坐标＋稳定显示缓冲”，每项单独与旧版对照；若内存没有下降或驻留容量反升，应保留失败证据并调整，不能把方案写成已优化成功。

1. 同输入检查顶点/法线/颜色、三角形次序与部位，随机和边缘落点查询结果；保留旧实现作为测试时请求拦截基准，不改历史基线。
2. 核对显示雪面与落点共用数据，旋转/搬动/删除/撤销/专属部位替换后没有过期索引或误释放。
3. 同一机器条件、画面尺寸与 DPR，分别测 6/12 栋的首次下雪、稳定厚雪、持续积雪与雨融；额外区分“相同素材多实例”与“不同素材种类增加”。
4. 记录主线程/Worker 数组、WebGL 创建/更新/删除量，以及隔离浏览器进程私有提交量，避免把进程数值当成某一类缓冲的精确大小。
5. 加入持续多轮积雪/融雪和编辑操作检查，观察是否趋于稳定，不用强制 GC 制造低峰值；沿用 1800 MiB 诊断目标及 1900 MiB 测试保护停止，二者均不等于浏览器硬上限。
6. 使用独立存储；复验当前/旧文件导入、非法输入原子拒绝和刷新恢复。正式存档与运行代码在本轮保持不动。

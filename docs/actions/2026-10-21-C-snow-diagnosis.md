# C：雪景高内存诊断与保真修改措施

## 状态与范围

Completed（诊断与修改措施交付；正式修复尚未实施）。用户要求用诊断技能定位当前雪景内存过大的 bug，并给出不降低精细度及逻辑的具体修改措施。本轮完成复现、最小化、单变量验证与建议，不自动把试验改动写入正式代码。

- 使用 `diagnosing-bugs`（本机没有单独名为 diag-bug 的技能）、`project-control-report`；为诊断脚本与记录使用 `action-document`。
- 当前代码已有上一轮预准备与共享 Worker 优化。历史 1454 MiB 是测试 Chrome 进程树私有提交量，不能全称为雪几何占用或已证实泄漏。
- 保留原雪层位置/法线/颜色、薄厚覆盖、遮挡、时间规则、建筑、布局与存档。无需用户选择画质降级。
- 复用 4173，不启停服务、不跑全项目回归、不提交推送发布。独立 Chrome 与审看存储，不覆盖正式地图。

## 诊断措施

1. 先复用已有内存检查，建立可失败信号。1200 MiB 仅作本轮诊断触发线（便于抓取当前高占用），不是用户确认的产品上限。
2. 缩小场景并复现；分清无雪基础、积雪增量、工作线程、主线程及 GPU 进程。记录浏览器实际图形后端。
3. 在拿到复现后提出 3–5 个可证伪假设；只在隔离页面/浏览器中逐项改变一个变量。需要试验源码时使用 Playwright 请求拦截，不覆盖正式文件。
4. 对确认原因列出具体修改位置、资源所有权/失效条件及保真验收；未验证的猜测单列，不能作为已定位 bug。

- 后续诊断命令、单变量、时序与判据随实际执行补记。优先使用真实进程私有提交量、CDP 主线程/Worker 堆、WebGL 资源活跃字节与分配/释放次数，避免把慢帧率当成内存泄漏。

## 自检结果

### 反馈回路和最小化

- 上述基线命令实际失败：3.646 秒观测 1234.996 MiB，触发 `MEMORY_LIMIT`；当时 GPU 进程约733 MiB、主应用 renderer约387 MiB。主线程已用 JS 堆约46 MiB、数组后备约95 MiB，Worker已用堆约3 MiB、后备约64 MiB。总提交量不可当作雪对象常驻量。
- `node scripts/inspect-snow-memory.mjs --asset=sakura-house --hold=1 --heap --label=min-sakura --out=artifacts/editor/snow-diagnosis --seconds=12 --limit=1200` 通过，15.064 秒观测峰值1129 MiB、末尾1031 MiB；移除其他内容后不再触发1200线。
- `node scripts/diagnose-snow-memory.mjs --label=step-three --rounds=2 --gc`：仅3个建筑格、两轮晴/满雪/清雪完成。无雪1013.945 MiB、首次满雪1164.754 MiB；第二轮没有持续上升，清雪后雪池与Worker归零。实际 WebGL buffer 从约22.2 MiB升至68.0 MiB，清雪回到22.2 MiB；多出的约21 KiB是有界飘雪缓冲首次上传后留待复用。无“雪越下越多、清不掉”的证据。
- 图形后端实际为 NVIDIA RTX 4060 Laptop GPU / ANGLE D3D11，不是软件渲染器。无界面自动化、机器负载及驱动回收仍会影响数值；本轮没有复现标签页 Out of Memory 崩溃。

### 已展示并验证的假设

1. 闲置灯光/渲染资源未停用：若成立，隔离关闭这些资源应减少分配且不改画面。
2. 雪层生成产生大量短命对象：若成立，分配采样应集中在生成循环，回收后常驻量显著低于累计分配。
3. 显示/查询保留多余缓冲：核对实际缓冲与清雪回落；不能把渲染与碰撞确有用途的两类数据直接叫泄漏。
4. 反复晴雪导致泄漏：若成立，重复后活跃资源或回收后的后备内存应持续增加。

### 已确认问题 A：未使用灯槽仍分配阴影

诊断入口均为 `node scripts/diagnose-snow-memory.mjs`：

| 实际参数 | 结果 |
| --- | --- |
| `--assets=sakura-house --rounds=0 --label=idle-before --assert-idle-shadows` | 失败：4个强度0的聚光灯均有1024×1024阴影目标；总974.137 MiB、GPU658.500 MiB |
| `--assets=sakura-house --rounds=0 --label=idle-after --probe=idle-shadows --assert-idle-shadows` | 隔离试验通过：闲置阴影0；总942.063 MiB、GPU624.480 MiB。GPU约减少34.0 MiB |
| `--assets= --rows=0 --rounds=0 --label=min-empty --assert-idle-shadows` | 最小化到空地图、无建筑、无雪仍失败：4个闲置阴影。因此是编辑器资源管理问题，并非雪粒子专有问题 |

检查来自实分配的 `light.shadow.map`，不是仅看 `castShadow` 参数。试验只改变 `lighting.js` 的未分配分支，不修改活动灯描述。

### 已确认问题 B：雪层和遮挡热路径分配过多

`node scripts/diagnose-snow-memory.mjs --label=profile-nine --rows=3 --rounds=1 --profile --gc`：九格、三栋原建筑；从满雪依次请求 .4/.75/1，三次全镇重建。采样包含期间已被GC回收的对象，**累计估计分配** Worker **2889.923 MiB**、主线程 **726.116 MiB**；不是同时常驻或峰值。主要归因：

| 调用位置 | 采样估计分配（MiB） | 代码核对 |
| --- | ---: | --- |
| `snow-geometry.js:setAmount` | 1245.359 | 每个裁切面重新创建 poly/masks、top/bottom 向量数组、中心/法线向量和遍历用小数组 |
| `snow-geometry.js:weld` | 357.023 | 逐顶点量化、临时数值/字符串；需保持原舍入语义，不直接换低精度 |
| `snow-surfaces.js:triangle` | 267.421 | 每次创建三角形对象、法线与边向量；有的调用仅使用面积分母 |
| `rain-surfaces.js:sample` | 243.703（主线程） | 每片雪花查询创建坐标向量、点/法线数组与结果对象 |
| `snow-surfaces.js:sample` | 68.263（主线程） | 返回最高面时创建法线等结果；飘雪本身只用高度与表面标记 |

实际总进程采样从无雪1126 MiB到满雪约1250 MiB、三次重建后1311 MiB；仅作诊断的强制GC后1147 MiB，Worker仍有约29.9 MiB必要后备数据；清雪后Worker和雪池归零。说明短期分配/延后回收确实推高占用，不能把累计2.89GiB写成常驻泄漏。生产环境不得用强制GC作为修复。

### 已确认问题 C：默认画布重复抗锯齿

源码同时给默认画布开了 `antialias:true`，又使用4采样离屏场景目标；最终画布接收的是全屏输出。隔离试验仅关闭默认画布抗锯齿，原离屏4采样、分辨率、曝光和后处理全部保留。

- `--label=step-three-aa --probe=canvas-aa --rounds=2 --gc`：两轮完成；GC后的满雪 Worker后备连续两轮均为30,052,630字节，主线程后备连续两轮均112,912,695字节。没有持续增长的证据。
- 固定时钟画面对比命令：`--label=capture-base --rounds=1 --capture`、`--label=capture-aa --probe=canvas-aa --rounds=1 --capture`、`--label=capture-idle --probe=idle-shadows --rounds=1 --capture --assert-idle-shadows`。
- 三张完整PNG SHA256均为 `fcff0cc72c02ee41e5f528068ad43a5879faafb34ed4b21678be87f27304536f`。已实际查看基准图。画面是固定下午、厚雪、停止飘雪用于稳定像素比较；不能据此宣称所有时段/缩放/DPR已经验证。
- 基准与画布试验初始GPU私有提交量675.656→641.398 MiB，约减少34.3 MiB。三栋关闲置阴影试验初始GPU659.086 MiB，符合只有2个闲置槽可省的方向。不同试验收益不能简单相加，进程数值有波动。
- `capture-base` 与 `capture-idle` 分别在1200.473/1202.059 MiB触发总量诊断线，脚本退出1；**不是画面比较或闲置资源断言失败**。`capture-aa` 全过程在该线内完成。没有修改1200线让原失败变绿。

## 具体修改措施（建议，尚未正式实施）

| 优先级 / 位置 | 修改做法 | 保真与资源边界 |
| --- | --- | --- |
| P0 `assets/shared/snow-geometry.js:setAmount`、`snow-surfaces.js:triangle` | 为一次串行计算准备固定容量的裁切数组、上下表面向量、法线/中心向量；每面重置长度并复用。只用面积的路径直接算原分母，避免建立完整三角形对象；逐标量写入替代热循环 rest参数/小数组。固定坐标的重复量化可复用，但新裁切交点保留原计算 | 不改原面数、顶点顺序、插值、舍入或法线混合；不可将临时向量引用存入已显示帧。保留单Worker、最新请求与有界缓冲；不降低更新频率 |
| P0 `editor/rain-surfaces.js`、`assets/shared/{snow-surfaces,snow}.js`、`editor/snowfall.js` | 给内部热路径增加调用者传入结果容器的查询，或同等精度的高度专用查询；复用坐标/法线临时向量。飘雪读取当下最高表面高度与标记，原返回独立结果对象的公共接口保留给其他调用者 | 不需要给每片雪花新增落点缓存；不减少雪花数、不降低遮挡查询频率、不放宽误差。即便继续每帧查询，也可先消除结果对象的反复创建；搬动/旋转/雪面变化继续立即取真实表面 |
| P1 `editor/lighting.js:update/dispose` | 无灯描述的槽位设置 `castShadow=false`；已有阴影资源在退出使用时释放并清空引用，重新分配时恢复描述并标记重建。初次未用不创建目标 | 不改活动灯位、目标、亮度、色温、阴影尺寸。释放的是宿主拥有资源，不动B建筑。初始化的关闲置试验已验证；“先使用再停用再启用”的释放/重建需正式修改后补测 |
| P1 `dist/main.js` | 默认画布改为 `antialias:false`，保留原离屏场景4采样和整个输出链 | 当前固定画面逐字节一致；还需四时段、近景、旋转/缩放及不同DPR比较。不能把它误改成关闭场景抗锯齿 |

### 正式实施后的通过条件

1. 原15组几何完整摘要逐字节一致，薄雪空隙与体积不变；若更改准备数据的结构，必须更新版本与重建，不跳过校验。
2. 原1200屋面射线、5043查询对照、新增边缘/四向/变换/雪量查询对照全部通过，原容差不放宽。
3. 固定像素对比和四时段近景核对；灯槽启停/删除/撤销不能残留或丢失有效阴影。
4. 相同输入、相同采样配置复测累计分配，确认热点分配下降；另做无Profiler的真实进程峰值测试。不能用Profiler或GC实验数字代替运行收益。
5. 重复积融雪、释放/重建，以及更多建筑的分级压力检查；资源释放必须稳定，不先承诺特定设备可装多少栋。

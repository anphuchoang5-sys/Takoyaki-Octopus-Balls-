# 建筑与地图的环境接口约定

2026-10-20。**以下为用户已认可的约定；C v2.7 已接通真实贴合的通用积雪与按部位专属替换；时段、降水和保存沿用 v2.6。建筑专属美术未接管。** 当前接口差异和所需适配见[状态表](building-status.md)，数值、未定字段及技术选型见[待定清单](open-questions.md)。

## 1. 输入由地图统一提供

| 内容 | 目标语义 | 当前与未来的区别 |
| --- | --- | --- |
| `time` | `morning`、`afternoon`、`dusk`、`night` | 三栋与全镇已接通；樱家自身色阶沿用、みつや早晨沿用下午 |
| `weather` | 当前任务支持 `clear`、`rain`、`snow` | 编辑器已接通晴雨雪；其他建筑字符串不代表全镇支持其他天气 |
| `snowAmount` | 0～1 的统一积雪程度；每栋按自身形状解释厚度与覆盖 | 统一状态、地图地面及三栋通用承雪已实现；专属建筑美术仍由原分工后续制作 |
| 季节 | 独立于时段／天气的建筑装饰选择 | 目标概念已确认；字段、取值、初始状态及具体内容未定，暂不向现有接口传入 |

当前调用形式如下；参数接收与雪景美术完成仍分开验收：

```js
asset.setEnvironment({
  time: 'dusk',
  weather: 'snow',
  snowAmount: 0.6
});
```

地图保存全镇状态，统一计算积雪／融雪进度。建筑不各自累计出不同的街区雪量，也不自行读取系统时间决定时段。修改天气不改变时段或清空积雪，修改时段不改变天气。

### 已确认：通用与专属积雪按部位兼容

2026-10-20 讨论决定；2026-10-21 用户认可小样、授权推广后，C v2.7 已实现以下按部位兼容规则。专属建筑造型仍由原美术分工负责，不等于本轮交付了专属成品。

- 没有专属雪景的部位使用通用效果；提供专属雪景后，替换对应部位的通用效果。同一栋建筑允许混用，不要求整栋二选一。
- 替换以实际部位为单位，例如主屋顶或某一棵庭院树；不能因为一棵树有专属雪景，就关闭整座庭院的通用积雪。
- 同一部位只生成一套雪，通用与专属不能叠加。建筑内部替换不影响地图公共道路的积雪。
- 两者都由地图同一 `snowAmount` 驱动，不另建积雪时钟；具体形状与最终厚度可以不同。
- 专属效果也须连续经历零星附着、连续薄雪、厚雪成形，并支持融雪恢复无雪外观。只有厚雪状态的静态成品，不等于完整的环境响应交付。
- 当前实际显示的雪面用于降水落点查询，替换后雪花和雨滴不能继续落到旧通用雪面或穿进专属雪层。

例如，樱家可以使用精做的专属屋顶雪，普通灌木继续用通用雪；以后只精修其中一棵庭院树，也只替换这棵树的积雪。这是兼容方式示例，不表示已给樱家安排了新的制作任务。

`asset.snow.getInspection().parts` 列出当前部位 ID；`replacePart(id, factory)` 接收返回 `root/setAmount/sample/dispose` 的专属工厂，传 `null` 恢复通用。坐标为建筑局部坐标，隐藏对应通用材质组并同步排除其查询；具体使用见[当前交接](../handoffs/C-town-editor.md)。既有“一栋建筑一个文件夹”和制作分工保留，不因这项决定自动转交或扩大任务。

## 2. 保留小而明确的方法集合

既有工厂继续返回建筑 `root` 和稳定身份／版本信息，保留原对象及必要旧字段。统一的是职责和含义，不要求一次重写所有资产。

| 方法 | 接收方责任 |
| --- | --- |
| `setEnvironment(patch)` | 接受环境变化，更新本建筑材质、可见灯具、亮窗、装饰及灯光需求；缺省字段保留原状态 |
| `getLightingDescriptors()` | 返回当前实际需要的灯光描述，颜色／强度／方向等已结合本建筑规则计算；无真实光源需求可缺省或返回空列表 |
| `updateEnvironment(elapsedSeconds)` | 需要持续动画时使用宿主统一累计秒数；不使用帧数作为积雪速度，无动画则不需要此方法 |
| `dispose()` | 释放该实例拥有的资源，不释放其他实例、共享缓存或编辑器的灯池 |

非法输入不能让本建筑停在一半更新的状态。全镇选择和文件导入也需要先校验再应用，失败后不能只更新部分建筑。具体全镇失败恢复办法列为实现前技术设计项。

现有 `getEnvironment()` 与 `getEnvironmentState()` 可以继续用于检查，不在这次约定中强行统一改名。便利店既有 `update(dt, visitor)` 不能当成 `updateEnvironment(elapsedSeconds)` 调用。

## 3. 共用计算与建筑特点

- 共用时段、夜灯开启方式等规则只维护一份，建筑使用共用计算加自身配置／例外。
- 建筑负责把这一结果应用到自己的灯具外观、亮窗、材质和灯光描述；灯具看起来发光与实际照明不能一边开一边关。
- 编辑器控制全镇太阳、环境光、背景及曝光。建筑不能修改全局场景或另一栋建筑来达到自己的效果。
- 樱家使用自身动画色阶，みつや普通材质会实际受光。需兼容这种差异，不能给所有材质强套同一个染色／自发光修正。
- 返回的灯光强度是当前目标强度，编辑器不再乘一次时段系数。灯池限额影响实际分配，但不是另一套建筑美术规则。

建筑“早晨沿用日间”“黄昏使用过渡”“冬季未制作”需明确列出。能接受一个参数、存在一个方法或只记录字段，均不能代替视觉效果交付。

## 4. 灯光的位置与所有权

当前みつや描述已包含 `id`、`type`、`position`、`target`、`color`、`intensity`、`distance`，以及聚光灯／阴影参数；以其[现有实现](../../dist/town/assets/mitsuya/environment.js)作为接入事实依据。通用描述的必填项和默认值尚需做小范围字段整理，不据此另建大框架。

1. `position` 与方向目标 `target` 都使用建筑 root 的局部坐标。编辑器更新世界矩阵后分别转换二者；缩放时同步处理有效照射距离。
2. 编辑器持有并复用实际光源与阴影资源，建筑提供需求，不在每栋资产中另建无限光源。
3. 有新描述时优先使用新描述；旧 `previewLamps` 仅作原日间兼容，不能与新描述重复消费。
4. 独立预览的灯光适配器只服务独立预览，不和正式编辑器灯池同时启用。
5. 樱家已有灯泡、光束、光斑等几何表现保留；没有灯光描述不等于没有夜景，不自动额外生成相同光效。
6. 当前编辑器有 10 个便利店 PointLight 和 4 个みつや SpotLight 槽位；接入先沿用限额，超出限额的远处表现如实说明，不能承诺每栋同时得到全部动态灯。

## 5. 调用与资源生命周期

1. 实例创建后、显示前继承当前环境；地图负责应用摆放变换和刷新世界矩阵。
2. 环境发生变化，先更新建筑环境，再读取新的灯光描述。旋转／搬动后，即使环境未变，也要更新灯的世界位置和方向。
3. 同一个宿主主循环提供累计时间；建筑不新增自己的 RAF 或独立时钟。
4. 放置预览继承环境，但不重复占用正式建筑灯池。撤销恢复、导入重建同样继承当前状态。
5. 删除或隐藏实例后，地图取消对应灯光分配，再按资源所有权释放实例。便利店共享资源不能用遍历释放的方式误删。
6. 积雪属于环境表现，不是新增占格建筑；持续变化不产生布局撤销步骤。搬走建筑后由地图重建该位置正确的地面覆盖。

## 6. 交付与验证

每次建筑交付附上：ID／版本、效果覆盖表（独立效果／明确沿用／未制作）、共用规则与例外、灯光和资源说明、预览入口、实际检查结果及待认可范围。表达形式先沿用 README／交接表，不新增尚未确定的强制元数据协议。

后续接入需验证：时段与天气互不重置；多实例隔离；四向旋转与搬动；删除恢复；夜晚建筑和道路可见；无重复布灯；新旧文件兼容。定向检查通过与用户画面认可分别记录，未运行不得写通过。

C v2.6 已在后续用户授权下实现街区v2封装，内部布局仍v1、原存储键不改；具体格式、旧文件策略、动态雪面采样及公开方法见 [当前编辑器交接](../handoffs/C-town-editor.md)。建筑雪造型当前分工与待补内容见 [初稿移交](../handoffs/C-building-snow-draft.md)。
